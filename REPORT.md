## 4. Пошук причин

Для цього завдання я зібрала ту саму production-збірку з картами коду (`npx vite build --sourcemap`),
щоб DevTools могли показати, яким рядкам вихідного коду відповідає стиснутий код. На швидкість це не впливає:
файл `.map` завантажують тільки DevTools. Трейси й скріншоти лежать у `report/01-diagnosis/`.

### Проблема 1. Прокрутка: хук useBioClamp змушує браузер перераховувати layout

**Гіпотеза.** Прокрутка гальмує не через JavaScript як такий (Scripting лише 1,2 с), а через Layout
(Rendering 20-22 с). Щось на кожну подію scroll змушує браузер перераховувати розмітку сторінки з 2000 карток.

**Що показав трейс** (`traces/scroll-forced-reflow.json.gz`, CPU 4x, 20 прокручувань за 31,4 с):
- на треку Main кожен `Event: scroll` → `Function call`, під ним смугасті фіолетові блоки Layout із червоними
  позначками forced reflow;
- insight **Forced reflow**: загальний час примусових перерахунків **14,43 с**, головна функція `y @ index-DILTU0nO.js`;
- за картою коду ці позиції ведуть у [src/hooks/useBioClamp.js](src/hooks/useBioClamp.js): функція `update` (рядок 12),
  а перерахунок викликають `getBoundingClientRect()` (рядок 14) і два читання `offsetHeight` (рядки 16 і 18).

**Причина своїми словами.** Для кожної видимої картки хук прибирає клас обрізання, одразу читає висоту тексту,
повертає клас і знову читає висоту. Щоб відповісти на кожне таке читання, браузер мусить негайно перерахувати
розмітку всієї сторінки, і так кілька разів на кожну подію прокрутки.

Скріншоти: [summary](report/01-diagnosis/screenshots/1-scroll-summary.png),
[insight Forced reflow](report/01-diagnosis/screenshots/1-scroll-forced-reflow-insight.png),
[код у Sources](report/01-diagnosis/screenshots/1-scroll-sources.png).

### Проблема 2. Сортування "Рекомендовані" перераховує рейтинг у кожному порівнянні

**Гіпотеза.** Клік ♡ не змінює порядок списку, але займає 2,4-2,7 с. Можливо, при кожному рендері `App`
список заново сортується, і саме сортування дороге.

**Що показав трейс** (`traces/click-favorite.json.gz`, один клік ♡, CPU 4x; клік займає 2387 мс processing):
- у Bottom-up на першому місці серед функцій **`weightedRating` (rating.js:12): self time 1136 мс, 19,4%** усього запису;
  `tutorScore` (rating.js:24), яка її викликає, total 1186 мс (20,3%);
- ланцюжок викликів у Bottom-up: `weightedRating` ← `tutorScore` ← `recommended` (catalog.js:13) ←
  `getVisibleTutors` (catalog.js:35) ← `App` (App.jsx:22) ← React ← `Event: click`.

**Причина своїми словами.** Компаратор сортування `recommended` для кожної пари репетиторів заново рахує бал обох,
а бал рахується довго: функція проходить усі відгуки, для кожного створює `new Date` і рахує степінь. Сортування
2000 репетиторів робить десятки тисяч порівнянь, тож бал того самого репетитора рахується десятки разів, і так
при кожному рендері `App`, навіть від кліку ♡, який порядок не змінює.

Скріншоти: [Bottom-up](report/01-diagnosis/screenshots/2-click-bottom-up.png),
[ланцюжок викликів](report/01-diagnosis/screenshots/2-click-bottom-up-chain.png).

### Проблема 3. Один клік ♡ перемальовує всі 2000 карток

**Гіпотеза.** Після кліку ♡ змінюється одна картка, але React рендерить увесь список.

**Що показав React Profiler** (dev-режим `npm run dev`, звичайне вікно Chrome без CPU throttling,
увімкнено "Record why each component rendered"; один клік ♡):
- один коміт, Render **844,8 мс**; `App` сам 400,7 мс (це сортування з проблеми 2), `TutorList` сам 9 мс,
  а **432 мс ідуть на дочірні `TutorCard`**;
- у вигляді Ranked у коміті рендеряться `TutorCard` з різними `key`, тобто картки, яких клік не стосується;
- для кожної `TutorCard` Profiler пише **"Why did this render? Props changed: (onSelect, onToggleFavorite)"**.

У production-трейсі того самого кліку (`traces/click-favorite.json.gz`) `TutorCard` має total 442 мс,
з них `formatPrice` 400 мс (до неї я повернусь окремо).

**Причина своїми словами.** `TutorList` при кожному рендері створює для кожної картки нові функції
`() => onSelect(tutor.id)` і `() => onToggleFavorite(tutor.id)`, а `TutorCard` не обгорнута в `memo`. Тому будь-яка
зміна стану в `App` (обрані, відкрита картка, тост) змушує React заново рендерити всі 2000 карток, хоча дані
змінились тільки в одній.

Скріншоти: [Flamegraph](report/01-diagnosis/screenshots/3-profiler-flamegraph.png),
[Ranked і "Why did this render"](report/01-diagnosis/screenshots/3-profiler-why-rendered.png).

### Проблема 4. CLS 0,41: у картинок немає розмірів

**Гіпотеза.** Сторінка стрибає, бо фото й банер до завантаження мають висоту 0, а коли браузер дізнається
їхній розмір, усе, що нижче, з'їжджає вниз.

**Що показав трейс** (`00-baseline/traces/s1-load-run1.json.gz`):
- трек Layout shifts: **один зсув на 13,85 с, score 0,409**, це і є весь CLS. Insight "Layout shift culprits"
  винуватця автоматично не назвав ("Couldn't detect any layout shift culprits"), тому я подивилась сам зсув;
- за подіями мережі в цьому ж трейсі: запити на картинки стартують на 12,4 с (поки йшов довгий рендер, браузер
  про них не знав), перші відповіді приходять на 13,26 с, а через пів секунди, на 13,85 с, стається зсув;
- зсунулись: `div.hero__text` (опустився приблизно на 300 px, бо над ним з'явився банер), `main.layout`
  (весь каталог з'їхав униз), і три перші `article.tutor-card` взагалі вийшли за межі екрана;
- у CSS у `.hero__image` і `.tutor-card__photo` стоїть `width: 100%; height: auto`, а в тегах `<img>`
  ([Header.jsx](src/components/Header.jsx), [TutorCard.jsx](src/components/TutorCard.jsx)) немає `width` і `height`.

**Причина своїми словами.** Браузер не знає пропорцій картинки, поки не прийдуть її перші байти, тому спочатку
відводить під неї 0 px висоти. Коли розмір стає відомим, банер і фото раптом займають місце, і весь вміст під ними
стрибає вниз.

Скріншот: [трейс зі зсувом](report/01-diagnosis/screenshots/4-load-layout-shift.png).

### Проблема 5. LCP 25 с: банер чекає рендеру і ділить канал із 36 фото

**Гіпотеза.** LCP складається з двох частин: спочатку браузер не знає про банер, бо головний потік зайнятий
рендером, а потім банер повільно вантажиться, бо одночасно з ним качаються всі фото.

**Що показав трейс** (`00-baseline/traces/s1-load-run1.json.gz`, Fast 4G, CPU 4x), insight **LCP breakdown**:

| Частина LCP | Тривалість | Що це |
|---|---|---|
| Time to first byte | 168 мс | HTML прийшов швидко |
| Resource load delay | **12 247 мс** | банер `hero.png` почав вантажитись лише на 12,4 с |
| Resource load duration | **7352 мс** | банер вантажився 7,4 с |
